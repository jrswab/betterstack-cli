# Milestone 005 Implementation Guide — `bs incidents timeline <id-or-url>`

Spec: `docs/plans/001_betterstack-cli-first-release_005_spec.md`. Milestone source: `docs/plans/001_betterstack-cli-first-release_milestones.md` (entry 005).

## Section 1: Context Summary

Milestone 005 turns `bs incidents timeline` from a "not implemented" vector into a working command on the existing 004 seams: one bearer-authenticated `GET /api/v3/incidents/{incident_id}/timeline` request whose target follows the same narrow positional `<id-or-url>` rule as `bs incidents get` (opaque bare ID, or dashboard URL of the observed form `https://incidents.betterstack.com/team/<team-id>/incidents/<incident-id>` resolved by `resolveIncidentTarget`), with no pagination — no `--page`, no `--per-page`, no filters, an empty query string — and the raw byte-for-byte body passthrough including heterogeneous timeline items (`timeline_truncated`, object-valued `comment` content, composite string IDs), with no completeness promise and no truncation notice of the CLI's own. The 002/004 credential, error, timeout, no-redirect, no-retry, and token-safety rules are reused unchanged through the shared executor `doMonitorsRequest`. All behavior is verified through the `runWithAPI` injection seam against mock loopback servers using only the dummy token; no live API is called. Constraints that bind every task: every shell begins with `unset BETTERSTACK_UPTIME_API_TOKEN` **and** `unset BETTERSTACK_API_TOKEN`; the test toolchain is `GOTOOLCHAIN=go1.26.9 GOPROXY=off`; `verify-incident-id.sh` and `.wayfinder/` stay untouched; only the `incidents timeline` vector changes outcome (`incidents get` behavior is frozen; `incidents list` stays not-implemented for 006).

## Section 2: Implementation Checklist

New product code stays in the existing file `cmd/bs/incidents.go` (package `main`); new tests in the existing file `cmd/bs/incidents_test.go`; the only pre-existing files touched are `cmd/bs/main.go` (one routing branch) and the regression test's case list in `cmd/bs/monitors_test.go`. Dependencies are sequential: A1 → B1 → B2 → C1. No task pair is parallelizable (single package, shared seam). Follow TDD within each task: write the failing test first, then implement, then run the focused test. Mock servers use `httptest` on loopback and the fixed dummy token `dummy-token-for-tests`; the ambient environment is never read by tests.
